# Agent Note: Tag-triggered ARM64 artifacts

Status: implemented

## Problem

版本标签需要触发可下载的 macOS ARM64 构建。现有构建脚本已拥有应用组装、框架嵌入和本地签名；现有正式发布脚本还要求发布者钥匙串中的 Sparkle 私钥。用户明确选择仅上传 Actions 构建产物，因此不能把构建成功扩大为自动发布更新。

## Decision

本记录保留标签构建和版本编号的决定；仅上传 Actions 产物和全流程只读权限的边界已由 [DMG 与 Release 发布](2026-10-31-dmg-release-assets.md)部分取代。

工作流监听版本标签推送，使用固定 macOS 15 ARM64 执行环境，并在运行时确认架构。第三方 Actions 固定到已核对的提交，令牌仅授予仓库读取权限，检出后不持久化 Git 凭据。

手动重试入口接受已有标签，并同样检出完整标签引用，服务于推送事件未生成运行记录或产物已过期的恢复场景。自动触发和手动触发共用构建步骤与并发组，避免维护两套构建流程。

`build-tag.py` 复用原有构建脚本，仅拥有标签元数据、归档与归档后验证。标签作为进程参数传入并严格验证，不拼入可执行 shell（命令解释器）代码。完整提交历史拥有构建号，避免工作流重新运行导致同一提交版本漂移；跨分支发布仍由发布者确认构建号顺序。

上传完整 ZIP 及校验值，不上传裸应用目录，避免产物服务改变框架符号链接和可执行权限。输出在临时目录完成校验后才进入最终目录，已有产物拒绝覆盖；上传步骤仅在前序检查成功后运行，且缺少文件时失败。

## Alternatives considered

- 同时自动创建正式 Release 并上传签名清单：超出用户选定范围，也需要将签名私钥交给云端；仍由[签名更新方案](../feature/2026-10-31-signed-app-updates.md)拥有正式发布边界。
- 在工作流内复制应用构建命令：会与本地框架嵌入和签名步骤分叉，故复用已有脚本。
- 使用漂移的 `macos-latest` 或 Intel 执行环境交叉编译：增加环境变化或架构误判，当前只需一个 ARM64 构建。
- 使用工作流运行次数作构建号：编号取决于工作流历史，而非源码提交；重新配置工作流时可能回退。

## Consequences

无需云端私钥，构建产物只用于手动分发和验证，不会触发客户端自动升级。构建依赖 GitHub 提供的 macOS 环境与网络，超时或失败可在运行页面重试。工作流文件必须先到达被标记的提交才会生效；本地验证不能证明托管执行环境或产物上传成功。

触发格式、版本来源、保留期限和复现方式由[标签自动构建参考](../../../app-updates.md#标签自动构建)拥有。
