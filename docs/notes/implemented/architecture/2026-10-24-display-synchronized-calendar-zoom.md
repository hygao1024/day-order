# Agent Note: Display-Synchronized Calendar Zoom

Status: implemented

## Problem

月年缩放用固定 8 ms 睡眠驱动，不能与显示器刷新对齐；每帧重新测量 SwiftUI 上下栏、强制整棵视图布局，并重复构造日期映射及查询字体权重。即使缓出曲线连续，额外唤醒和主线程重复工作也会增加交接延迟与帧间波动。

## Decision

运动节奏、内容淡化和中途重定向现由[连续日历运动](../bug-fix/2026-10-24-continuous-calendar-motion.md)取代：原有 220 ms 三次缓出、上下栏文字直接更新及反向直接结束不再是当前行为。本文保留快照端点、常驻容器、显示刷新驱动和生命周期约束的原始理由。

展示控制器将过渡分成准备与显示刷新两个阶段。准备任务在模型赋值后刷新并完成目标布局、取样，不再等待固定 16 ms。保留赋值后补发通知，防止 Published 在赋值前取样消费旧状态。只在实际取得终点后启动 NSView 的 CADisplayLink（显示刷新回调），用目标刷新时间戳推进动画；最初沿用约 220 ms 的三次缓出和约 120 ms 的减少动态效果降级。

刷新回调复用已配对并排序的日期端点及字体权重，只计算位置、字号、权重、颜色和容器尺寸。仍用原生文字绘制，避免预渲染整组位图在放大时失去清晰度。临时层不缓存全年日期，成本随可见日期而非年份范围增长。

CalendarShell 在实际动画开始时冻结终点的头部、正文和底部尺寸。逐帧只调整固定上下栏的裁剪容器位置和弹窗尺寸，不请求整棵 SwiftUI 视图同步布局；完成或取消时释放尺寸缓存。正常完成后重新测量实际内容，接纳过渡期间可能改变的详情高度。非动画状态的布局仍由原有内容决定。

准备任务继续使用修订号拒绝迟到结果；显示刷新回调只接受当前驱动实例。结束、快速反向、设置、关闭和退出都注销刷新驱动，再恢复正文和外壳。回调目标弱引用控制器，避免运行循环持有刷新驱动而延长控制器生命周期。显式取消路径不在 Published 的赋值前同步重测目标页面；正常完成路径可重测。

本决定替换[日期缩放过渡](../feature/2026-10-24-calendar-zoom-transition.md)的固定睡眠驱动和[常驻日历外壳](../bug-fix/2026-10-24-persistent-calendar-chrome.md)的逐帧尺寸测量方式。日期选择、原生列表复用、滚动位置恢复、只有日期正文缩放及上下栏常驻保持不变。

[设置容器过渡](../feature/2026-10-24-settings-container-transition.md)复用同一驱动与取消路径，设置往返只插值容器、不配对日期；这里的显示同步和短期布局缓存约束继续适用。

## Alternatives considered

- 仅缩短时长或改变缓动曲线：不能减少逐帧布局与重复唤醒；保留已确认的运动节奏，先移除这些工作。
- 继续使用定时睡眠但将周期设为 16 ms：仍无法与不同刷新率或屏幕迁移同步，系统已有与视图所在显示器关联的回调。
- 将所有数字、卡片和弹窗分别交给独立图层动画：弹窗和真实上下栏仍需要统一时间轴；当前范围保留一个刷新进度，避免引入多套终点与取消状态。
- 预生成每个字号的日期位图：增加准备时间和临时内存，并可能降低放大清晰度；只预计算不随进度改变的配对与字重信息。

## Consequences

真实入口记录准备、逐帧更新和绘制耗时以及显示刷新时间戳，以便同机比较。回归按真实状态等待完成并设超时，检查中间位移、快速缓出、固定外壳、开始前取消、运行中取消与结束后的回调静止。诊断计数只在调试构建存在；临时移除驱动注销必须触发“结束后仍有回调”的负向检查。

采样包括应用主线程和主动截图的成本，不能直接证明物理屏幕丢帧率；不同显示器刷新率、系统负载和桌面材质合成仍需实际体验。冻结布局只持续一次短过渡，不作为长期布局缓存。
