# Agent Note: Native Offline Calendar

Status: implemented

## Problem

日序需要把已确认的状态栏日历设计变成原生应用，同时避免将概念图中的错误农历日期固化为产品行为。首版只提供日历信息，不引入日程账户、同步或系统日历权限。

## Decision

采用 Swift Package 构建，AppKit 拥有状态栏、临时弹窗、键盘监控与唤醒通知的生命周期，SwiftUI 拥有月历、选中状态投影和本地设置。日期模块拥有月网格、官方日期资源查询和节日分类，应用模型拥有当前选择及导航边界。

农历和节气共同使用香港天文台公开表的离线资源，明确支持 1901–2100 年；农历以月首和闰月标记压缩保存，生成时对照逐日原表校验，运行时通过月首查找得到日序。设备时区只决定今天的公历日期，中国节日不转换为海外某个瞬间。

维护脚本优先直接读取原表，也支持带固定校验和的公开存档；存档模式对照已有官方缓存，差异必须人工处理，来源和已核对年份与资源一并保存。这个入口用于官网间歇性不可达时保持数据更新可复现，不允许静默接受任意镜像内容。

外部点击关闭的窗口承载现由[无箭头面板](../feature/2026-10-29-arrowless-calendar-panel.md)部分取代：NSPanel 拥有外框与关闭监控，保留原有页面和模型边界。局部键盘监控只在弹窗打开且事件属于弹窗时处理，关闭时移除；定时器和通知在应用退出时清理。数据读取失败会提示退出，避免把缺失资源默默呈现成“没有节气”。

## Alternatives considered

- 仅使用 SwiftUI 的菜单栏场景：代码更少，但 AppKit 对原生浮层尺寸、焦点和关闭生命周期的控制更直接，便于真实入口验证。
- 自写太阳黄经近似算法：不需要日期资源，但午夜附近的误差会改变节气所在日；离线官方表在明确年份范围内更容易核验。
- Foundation 系统中国历法：本机 macOS 15.5 在 2057-09-28 和 2097-08-07 返回农历日序 0；官方表分别为九月初一和七月初一。统一使用官方数据避免系统版本导致的差异，不为个别日期维护补丁。
- 引入完整第三方历法库：可提供更多历法计算，但首版仅需系统农历和节气日期，额外能力和更新依赖不值得引入。
- 在线查询日期：引入联网失败和缓存一致性问题，不符合随时可用的轻量工具定位。

## Consequences

历法查询没有外部依赖和网络请求；放假安排的手动更新由后续[holiday-cn 接入记录](../feature/2026-10-23-holiday-cn-schedule.md)拥有，扩展了应用的联网边界。构建不依赖开发者账户或完整 Xcode，但分发前仍需要正式签名与公证。日期资源更新需要通过维护脚本显式进行；扩展年份范围或需要节气精确时刻时，应重新评估数据来源和表示。

日期模块通过已知节日、闰月、月网格和时区样例验证；调试入口复用真实状态栏、应用模型与生产视图生成截图，检查导航边界和关闭清理。它不替代人工鼠标交互、旁白和多系统版本验证。
