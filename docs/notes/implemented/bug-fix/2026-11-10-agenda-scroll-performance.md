# Agent Note: Agenda Scroll Performance

Status: implemented

## Problem

[当天日程展开](../feature/2026-11-10-inline-day-agenda.md)后，滚动导致周行反复配置、日程标题重复测量，跨月查询还会因其他日期变化重新准备详情动画。大量日程的周行重新进入视口时，一次创建全部原生事件行形成主线程尖峰。单纯缓存布局无法消除全量创建视图的成本。

## Decision

部分取代原记录的全量行视图和展开时统一重采策略，保留固定窗口、独立列表滚动及视口外周行连续平移的约定。

模型仅缓存当前展开日期的一份不可变布局。日期、状态文案或当天事件改变才重新生成布局；全局事件修订变化但当天数据相同时复用布局。协调器以布局引用识别内容变化，缓存详情所在周，避免每次行高查询重复定位日期。关闭详情清除模型缓存，详情视图清空时同时释放布局和事件子视图。

事件行只按内层滚动视口及上下少量预留范围创建，完整事件和高度仍保留以支持到底与剩余数量。使用内层裁切范围而非外层日历的可见范围，避免动画采集屏幕外端点时丢失详情内容。

展示控制器比较展开日期的事件，只有内容实际变化且详情可见时重新准备布局动画。其他日期更新或详情在屏幕外时由真实表格刷新；导航期间不重新准备详情过渡的例外由[会话内保留展开状态](2026-11-10-agenda-navigation-retention.md)拥有，防止数据补回接管返回运动。未展开时继续沿用[切档启动优化](2026-11-06-calendar-mode-latency.md)的标记更新路径。事件源、权限和异步代际边界保持既有所有权，不新增查询或跨日期缓存。

## Alternatives considered

- 只缓存测量并减少周行配置：确实减少重复工作，但 200 项场景中重新创建全部视图的峰值仍约 59 ms，不能独立解决卡顿。
- 全部事件行长期常驻：可以减少重建，但内存和原生视图数量随单日日程增长；有限内层视口不需要同时持有全部行。
- 直接跳过展开后的事件刷新：会留下过时标题和高度；必须区分其他日期变化与当天内容变化。

## Consequences

真实原生滚动专项覆盖 12／200 项、收起／展开、跨月往返、最后一项可达、布局复用以及无关／当天事件更新。临时恢复全量创建时，行数检查必须失败；恢复后复验。原交互专项继续约束固定窗口、边缘动画、内部滚动和隐藏后的迟到结果。

同机调试采样中，200 项展开场景的最大同步耗时由约 59.2 ms 降至 10.8–11.5 ms。该数据覆盖滚动、布局和同步绘制，不包含全部异步工作，不能当作屏幕帧率或跨设备承诺。[单行日程](../feature/2026-11-11-agenda-single-line-rows.md)移除标题换行测量，高度数组仍随事件数量线性增长；当前优化限制昂贵原生视图的数量，并未引入无限数据规模的保证。旁白完整操作和物理触控板体验仍需实机验证。
