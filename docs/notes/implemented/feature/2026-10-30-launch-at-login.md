# Agent Note: Launch At Login

Status: implemented

## Problem

菜单栏日历需要支持用户主动选择登录后自动启动；只保存布尔偏好无法反映用户在系统设置中撤销批准或服务登记失败的情况。

## Decision

使用 ServiceManagement（服务管理框架）的 `SMAppService.mainApp` 登记主应用，沿用已有签名应用包，不增加辅助进程或依赖。独立控制器由 AppDelegate 持有，设置页面读取系统状态并执行登记或注销，不在启动时自动修复或重试登记。

开关表达已登记，包含等待系统批准的状态；待批准必须同时显示尚未生效的说明和系统登录项设置入口，用户也可以直接关闭开关撤销。进入设置及应用重新激活时刷新状态，操作结束后无论成功失败都重新读取系统结果。开发裸可执行文件不允许登记。

此选项扩展[设置分组](2026-10-23-grouped-settings.md)与[设置容器](2026-10-24-settings-container-transition.md)的内容；既有显示偏好仍使用原存储，新登录项状态由操作系统拥有。

## Alternatives considered

- 在应用偏好中保存开关值：会与系统撤销、待批准和失败结果产生两个事实来源。
- 自行写入 LaunchAgents（启动代理）或新增登录辅助应用：当前系统最低版本已支持主应用服务，额外文件与进程增加安装、迁移和清理责任。
- 待批准时显示关闭：隐藏了已有登记，也不便直接通过开关撤销；采用开启加明确的未生效说明。

## Consequences

自动启动发生在用户登录后，保持菜单栏应用原有启动行为。系统签名、批准和应用路径仍决定实际可用性。同步注销只作用于主应用，系统不会终止当前日序进程。

冒烟沿用生产控制器和真实设置控件，仅在系统服务边界注入隔离状态，覆盖成功、待批准、错误、重试、外部修改和不可用入口，避免验证时更改电脑登录项。真实服务登记、系统批准及注销后重登录的启动效果仍需在可更改登录项的环境中人工验证，不能由隔离冒烟推断通过。

临时绕过执行层的应用包保护后，冒烟在“非应用包入口不应写入系统登录项”处失败，证明禁用规则有负向控制；随后恢复保护并重新构建。
