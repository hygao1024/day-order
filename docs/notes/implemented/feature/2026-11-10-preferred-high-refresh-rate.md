# Agent Note: Preferred High Refresh Rate

Status: implemented

## Problem

用户希望在设置中主动优先使用高刷新率。月年等过渡已有显示刷新驱动，但月初吸附、月份导航与返回今天仍以固定睡眠推进，不能通过同一偏好控制刷新节奏。

## Decision

CalendarRefreshPolicy 统一拥有应用动画的帧率请求策略。设置通过 AppStorage 保存偏好，展示控制器读取同一偏好，月视图由显式参数传入协调器。关闭时使用系统默认范围，开启时以所在屏幕最大帧率为首选、最高值，最低请求值不超过 60；每次回调重新检查屏幕能力和偏好。名称使用“优先高刷新率”，不承诺改变显示器模式或物理帧率。

月视图滚动动画改为 NSView 的 CADisplayLink，按目标呈现时间推进现有曲线与时长。此决定替换[月初吸附](2026-10-24-calendar-month-snapping.md)及其导航复用路径的固定睡眠驱动，并为[显示同步缩放](../architecture/2026-10-24-display-synchronized-calendar-zoom.md)增加偏好策略；手势滚动继续由原生滚动视图负责。

协调器拥有滚动驱动及单个完成 continuation（续体），完成与取消先失效驱动、清空续体再恢复等待任务。旧任务的取消必须匹配请求修订号，不得停止新驱动。窗口被遮挡或关闭时主动取消，因为不可见视图不保证还有下一帧；拆除时沿用统一取消和通知清理。减少动态效果直接设置终点，不启动滚动驱动。

## Alternatives considered

- 常驻高频定时器强制重绘整个面板：不能保证物理呈现频率，会增加静止时功耗。
- 只增加设置、不替换滚动动画驱动：偏好无法控制用户关注的吸附及月份导航路径。
- 固定请求 120 Hz：外接显示器能力不同，应使用所在屏幕上限；系统仍拥有最终调度。

## Consequences

高刷新率可能增加动画期间功耗；静止时不保留驱动，不修改系统显示设置。原生滚轮、触控板惯性以及 SwiftUI 控件自身动画仍由系统调度。该改动不替代绘制和布局性能优化，也不保证消除卡顿。

刷新率专项验证真实驱动请求、动态偏好、导航完成、新手势取消和关闭后无回调；关闭高刷请求的负向控制应使其失败。设置专项通过真实控件验证偏好写入，吸附与返回今天专项验证迁移后的行为。刷新时间戳只能证明回调节奏，不能作为物理屏幕帧率证据；不同显示器和低电量状态需实机确认。
