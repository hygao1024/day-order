# Agent Note: Signed application updates

Status: implemented

## Problem

设置需要可控的自动检查和自动安装，并从 GitHub 仓库获得 ARM64 正式版本。更新会安装可执行代码，下载成功不足以证明发布来源，也不能把替换正在运行的应用视为普通文件复制。

## Decision

使用锁定版本的 Sparkle，代替自有下载、解压、替换、权限提升和重启实现。`AppUpdater` 是设置与框架的连接点；Sparkle 拥有更新会话、调度及持久化偏好，应用不维护第二份开关事实。两个自动开关默认关闭，保持既有用户的离线启动行为；自动安装以自动检查为前提。

以 GitHub 最新正式 Release 的签名 appcast（更新清单）作为唯一更新入口，沿用用户明确选择的正式版本渠道。发布脚本从构建后的应用生成清单，拒绝预发布版本和非 arm64 主程序。无需额外托管服务或运行时 GitHub API（应用程序接口）版本解析。

清单与安装包采用 Ed25519 签名并在解压前验证，信任根为应用内嵌公钥。私钥仅在发布者钥匙串中。加入 Sparkle 是能力净增，剩余自有代码限于设置投影、构建嵌入与发布组装；框架升级时复验安装和签名拒绝路径。

## Alternatives considered

- 自行查询 GitHub API 并用脚本替换应用：省去框架，但需自有版本比较、下载缓存、签名校验、权限、取消和部分替换恢复，维护负担更大。
- 只打开 Release 下载页：不能满足自动下载并安装。
- 仅通过 HTTPS（加密传输）或同源校验和验证安装包：不能在更新服务器内容遭篡改时提供独立发布者验证。
- 将 appcast 放在仓库分支或独立网站：需要额外同步清单与附件生命周期；随正式 Release 发布可复用现有发布入口。

## Consequences

首次构建新增网络与二进制框架依赖，已下载依赖后日历仍可离线运行。发布者须保管签名密钥，且每个正式 Release 都上传匹配的 ZIP 与清单。签名不替代 Apple 公证；系统安装约束由框架处理。操作契约、密钥恢复和发布步骤由[软件更新参考](../../../app-updates.md)拥有。

真实回归使用隔离应用包、本地签名清单和 Sparkle 安装器，验证设置、拒绝篡改及实际替换；不会修改用户实际安装的日序。跨系统、授权提升、App Translocation（应用路径隔离）和已公证分发仍需另行实机验证。
